# Taste
- Prefers the agent to act as an orchestrator: split work across subagents (parallel explores, verification passes) and coordinate, rather than doing everything in the main session. Confidence: 0.75
- Wants a diagnose → review → implement loop when using subagents: one subagent investigates and proposes a plan, the orchestrator verifies/reviews that plan against the actual source, then a (separate) subagent implements the approved fix. Confidence: 0.7
- Expects root-cause fixes to be actually implemented in the repo by the agent (code changes made directly), not just diagnosed, reported, or handed back as manual run/refresh steps. Confidence: 0.65
- Wants free/cheap models (e.g. `minimax/minimax-m3.1-flash:free`) pinned per delegation for subagent work. Confidence: 0.6
- Values capability claims being demonstrated with a real throwaway test run rather than asserted. Confidence: 0.5
- Wants finished work written up in a repo file (not only summarized in chat), appended in whatever format/structure the existing doc already uses. Confidence: 0.6
- Prefers appending completed items to the project's existing task checklist (`TASKS.md`, sequential `- [x] T0NN description` entries) rather than creating a new standalone report/doc file, and cleaning up any file created by mistake. Confidence: 0.55
- Core/engine modules must not assume browser globals: guard DOM/UI notice calls (e.g. `showSystemNotice`/`showSystemMessage`) with `typeof document !== 'undefined'` (or equivalent) so headless Node tests and scripts do not crash. Confidence: 0.7
- Project convention: any change that adds/renames modules must update `docs/CODEMAP.md` (file index, lookup table, gotchas) and pass `node scripts/check_codemap.mjs` — the codemap is a checked, mandatory artifact. The codemap's import column must also be updated when an existing file gains or changes imports. Confidence: 0.8
- Expects the codemap checker to end green: if `node scripts/check_codemap.mjs` surfaces a pre-existing failure in an unrelated file, fix that stale entry in the same pass instead of finishing the task with a failing check. Confidence: 0.6
- Project constraint: browser-based verification is forbidden (AGENTS.md); all checks must run headlessly in Node via `scripts/*.mjs` wired into `npm run test:*` scripts. Confidence: 0.7
- Prefers one single source of truth module for cross-cutting state (e.g. `src/core/loadout.js`) plus a thin pub/sub event bus (`equipmentEvents.js`) over each scene/UI deciding the rules ad hoc. Confidence: 0.6
- Expects the final report structured as: root cause per file, files changed, test results with pass counts, an explicit "not done / assumptions" section, manual test steps for the user, and a closing "CODEMAP updated: yes/no" line — and capped in length (AGENTS.md: ≤15 lines) with exactly 3 manual test steps. Confidence: 0.75
- For bug-fix work specifically, wants each bug shown with its before-behavior and after-behavior, plus an explicit list of every file touched and every protected file touched (named, not just counted). Confidence: 0.6
- Project code conventions (AGENTS.md): one system per file, zero allocations in per-frame code (preallocate scratch objects/pools; no `new THREE.*` or closures in `update()` loops), hit payloads stay typed objects, and all balancing numbers live in `src/data/*` or `src/combat/CombatData.js` rather than inline in logic. Confidence: 0.75
- Project audio convention: exactly ONE WebAudio context in the game, created lazily and only after a real user gesture (browsers block a context built before the first interaction). All SFX route through the shared `src/core/AudioManager.js`; sound helpers return silently when the context is null and never create their own context; mute/volume are read through the shared helpers instead of `window.__audioMaster` directly. Confidence: 0.7
- Expects a full verification sweep before declaring done: `node --check` on every touched file, all npm test suites, codemap checker, and production build. Reinforced with a markdown link check across every doc (every relative link must resolve to a real file) and a grep for imports still pointing at deleted files. Confidence: 0.7
- Expects obsolete shared state to be deleted as part of the fix (old globals like `window.__tinkAudioCtx`, per-instance `this.ctx` / `this.audioCtx` fields) only after grepping every reader to confirm the migrated sites are the only users, so no dead code paths remain. Confidence: 0.6
- Reports bugs by pasting raw browser console output (stack trace or surrounding log lines) with no explanation; expects the agent to triage it, separate the real exception from benign `console.warn` noise, and fix only the actual error. Reinforced when a lone benign `console.warn` line (message + `file:line`) was pasted and expected to be addressed rather than dismissed as noise, and when an uncaught `TypeError` with a long repeated `animate` stack trace was pasted with zero prose, and when a raw three.js object dump (BufferGeometry with a NaN boundingSphere) was pasted with zero prose — no repro steps, no question, just the log. Confidence: 0.8
- When a runtime error surfaces, expects the agent to determine whether it is pre-existing (e.g. `git show HEAD:<file>`) rather than assume it came from the recent changes, and to label pre-existing vs. new in the report. Confidence: 0.6
- Prefers auditing sibling call sites of the same class after a missing-method crash (cross-check every `obj.method()` call against the class's defined methods) instead of patching only the reported one. Confidence: 0.6
- After fixing a numeric/geometry root cause (e.g. `Math.pow` on a slightly negative base yielding NaN), expects every other occurrence of the same construct to be grepped and confirmed already clamped/guarded, so the latent twin bugs are closed off in the same pass. Confidence: 0.6
- Scope discipline: leave unrelated pre-existing warnings/debug logs untouched and flag them as out of scope with an offer to fix, rather than bundling cleanup into the change — but when the user later pastes that same log line, it re-opens as an in-scope request to fix it. Confidence: 0.6
- Code-style convention: callback-style APIs (`onComplete`) must always invoke the callback so scripted/tutorial flows can never stall, even on early-return or guard paths. Confidence: 0.6
- Prefers defensive capability checks at integration boundaries: shared systems must tolerate both the new engine's entities and the legacy live-game entities (e.g. test for `c.stateMachine` before using it) instead of assuming one shape. Confidence: 0.6
- When a caller invokes a method the callee does not expose, fix the call site to use the callee's real API name rather than adding an alias/shim to the callee. Confidence: 0.55
- Prefers adding a missing accessor (e.g. a `facingYaw` getter) to the legacy class so it matches the new engine's convention, rather than changing the new engine's contract. Confidence: 0.5
- Final reports should explicitly flag which files are still untracked/uncommitted in git so the user knows what is not yet in HEAD — including anything deliberately left out of the commit (the tool's own preference files, scratch dirs) and any concurrently-running agent's work that got swept into the commit. Confidence: 0.6
- Treats noisy per-frame console warnings as a real defect to fix, not noise to ignore: prefers debouncing/deduplicating them (warn once per continuous excursion, only after the condition persists) rather than deleting the check, so genuine stuck/broken cases stay diagnosable — reinforced when a three.js "Computed radius is NaN" warning with a full object dump was pasted expecting a real fix. Confidence: 0.6
- Project rule (AGENTS.md): `src/world/*`, `src/gacha/*`, `src/hub/*`, `src/ui/*`, `src/player/Player.js`, `src/combat/Ally.js`, `src/combat/Enemy.js` are PROTECTED and need explicit user sign-off before editing; plans touching them should flag each file as protected and prefer new files over edits. Confidence: 0.75
- When a fix's blast radius spans several protected files, expects the agent to enumerate every affected site with the root cause, then present a scope question offering a recommended wider/shared fix (and a narrow one) for explicit approval before touching protected paths — approval then applies to the whole list. Confidence: 0.65
- Expects facts written into generated docs/prompts to be verified against the source before publishing: the agent spot-checked delegated (subagent) research, corrected two wrong claims, and surfaced a real pre-existing bug for the downstream implementer to fix or route around. Reinforced by a README rewrite where every claim (mouse mapping, npm scripts, key bindings, art budgets, directory listings) was re-checked against the code, wrong claims were corrected, and unimplemented features were moved into an explicit "known limitations" list rather than described as features. Line-number and file-path citations are not trusted either — the existing README's cited line numbers for dead code were stale, so every cited location must be re-grepped before being repeated. Confidence: 0.7
- Validates generated markdown deliverables programmatically (e.g. a fence-balance check on the written file) instead of eyeballing them, and re-runs `node scripts/check_codemap.mjs` after adding files. Confidence: 0.6
- Prefers fingerprinting the culprit from the error payload instead of broad scanning: grep the source for the distinctive attributes shown in the three.js dump (e.g. `setAttribute('color', ...)`, `drawRange`) and read the geometry builders (HeroRig.js, weapons.js) to pinpoint the object producing the NaN geometry. Confidence: 0.55
- Values reusing an existing mechanic or field when one already fits (e.g. the existing `hero.offenses` strike counter for lobby-law enforcement) over inventing a parallel system alongside it. Confidence: 0.55
- Avoids module dependency cycles: shared helpers used by several `src/core/*` modules are placed in a `src/data/*` module (or one canonical owner that re-exports it) rather than importing core→core. Confidence: 0.5
- Project UI convention: modal windows must be viewport-capped (e.g. `max-height: calc(100vh - 40px)`) and their inner columns scroll independently instead of letting content grow the window past the screen; they should also not leave dead space inherited from a base class (e.g. hiding the empty content element), and key/reference lists are laid out as 2-column grids of chips rather than one cramped column. Confidence: 0.6
- UI fix convention: when one window's layout is broken, find a sibling window that already solves the same class of problem (e.g. RosterWindow's viewport-capped panel with a scrolling body and a pinned action row) and mirror that exact structure in the broken window — don't invent a new layout mechanism, and don't change the shared base class the other windows still rely on. Confidence: 0.65
- UI convention: when the control scheme changes, every surface that documents controls must be updated in the same pass — all HUD hint-bar variants (per-class mage/archer/default strings), the options window's key-reference table, and tutorial dialogue / pre-deploy warning screens — so the on-screen instructions match the new behavior. Confidence: 0.75
- UI aesthetic preference: ornate, game-consistent chrome over plain browser defaults — gold accent bars with spaced section headers, segmented pill selectors where the active option is a gold glowing pill, hand-built switch toggles (hidden native checkbox driving a painted track/knob) instead of raw checkboxes, and monospace kbd chips for control references. Confidence: 0.7
- Expects settings that are already persisted and applied at load but had no UI control to be surfaced with real controls (e.g. a previously unreachable resolution-scale callback got a 50/75/100% segmented picker) rather than left hidden. Confidence: 0.6
- Project naming: "the options window" means the SYSTEM OPTIONS modal (`src/ui/OptionsWindow.js`); the roster's row of sort/filter buttons is a separate "sort bar" surface. Confidence: 0.6
- Control convention: the mouse is the camera authority at all times in gameplay — mouse movement over the game canvas steers the camera unconditionally (not gated behind holding a button, aiming mode, or dragging). Arrow keys remain only as a keyboard-only fallback. Confidence: 0.75
- Control convention: the OS cursor is hidden while the player is in the world and restored for any UI overlay (roster, options, command wheel); HUD/menu buttons keep their own pointer cursor so only the game canvas is pointer-less. Any overlay that presents a choice or dialogue (tutorial dialogue, equipment notice) must likewise show the cursor and be mouse-clickable — the rule must not depend on a narrow "system window" whitelist, and "the option appears but I can't click it" is a bug to root-cause, not a cosmetic tweak. Confidence: 0.75
- Control convention: mouse-look must be genuinely unlimited — the camera keeps turning however far the mouse moves, so the pointer has to be captured with real pointer lock (a merely CSS-hidden cursor stops at the screen edge and the rotation "runs out of screen"). Clicking the canvas captures the pointer, ESC releases it, and every overlay/choice must release the capture and re-acquire it on close. Confidence: 0.8
- Control convention: W/A/S/D only translate the character along fixed camera-relative axes and never rotate the camera — A/D is a pure strafe that keeps the body facing forward so the slide stays on one axis (no circling, no auto-turn behind the character). Confidence: 0.7
- Control convention: the canonical combat mouse layout is LEFT CLICK = ATTACK and RIGHT CLICK (HOLD) = BLOCK/shield. The options window may offer a mirrored layout, but the default, the saved setting, and every hint bar / tutorial / deploy-warning string must all state the same mapping. Confidence: 0.8
- Consistency invariant: settings defaults must be identical in the new-game path and the load-from-save path — a divergence makes the game silently behave differently after a reload (e.g. buttons flip and the attack button stops responding). Normalize already-saved games with a one-time migration flag rather than only fixing the fresh-start path. Confidence: 0.7
- UI correctness: a toggle's on/off state must be derived from the underlying value and its explanatory hint text must match that polarity — a switch that reads ON when the setting is off is a bug, not a wording nit. Confidence: 0.65
- Notification timing preference: a blocking modal prompt must fire only at the moment the player commits to the action that needs the decision (e.g. pressing ENTER FLOOR), never on passive surfaces like opening a window, walking around, or a tutorial step — passive states should use a non-blocking inline banner or a character speech bubble instead. Reinforced when the user asked for the prompt "only if i was going to go to a floor without a weapon, not always". Confidence: 0.75
- Game-flow design preference: a missing prerequisite should be presented as a choice, not a wall. When a prerequisite is unmet (no equipment, no upgrade), offer an explicit alternative path ("ENTER ANYWAY", proceed bare-handed) instead of a blocking message that dead-ends the interaction — the prompt should ask "do you want to X without Y?" and give both an "obtain Y" and a "proceed anyway" button. Confidence: 0.7
- UI aesthetic preference: prefers compact, dense modal panels — a small footprint with tight internal layout rather than a large, sparse dialog with generous whitespace (e.g. asked to "compact" the equipment-notice panel). Confidence: 0.5
- Town navigation convention: character routes (e.g. the Summoning Room exit) are authored once in the town layout data (`LAYOUT.zones[...].doorCorridor`) and consumed by every system (gacha walkout, tutorial walkout, nav-grid carve) instead of each system hardcoding its own waypoint list; routes must trace real walkable geometry (ramps, stairs) so characters never appear to jump or clip through railings, fences or terrace steps. Confidence: 0.65
- UI-vs-camera input separation convention: an open overlay must swallow camera-bound input (mouse-wheel zoom) without breaking native UI behaviour — stop the event on the overlay's root element with `stopPropagation` (never `preventDefault`, so inner lists still scroll natively) and mark that root with a dedicated class (e.g. `.mm-system-window`) that the input layer detects via `event.target.closest(...)`; scrollable report/list elements get `overflow-y: auto` + a `max-height` + `overscroll-behavior: contain` so scrolling never chains out to the page. Confidence: 0.65
- Prefers a fix to be implemented in the shared base class/helper so every instance inherits it (e.g. all system windows through `SystemWindow`), never a one-off patch on the single surface that was reported. Confidence: 0.65
- Walk-height convention (`src/art/town/WalkHeight.js`): the character stands on the terrain and on stairs only — never on props (boulders, crates, barrels) or raised building floors. A prop is one isolated blob above the ground so the ground can never reach it, while a staircase is a stack of small steps (`MAX_STEP_RISE = 0.6`) or an analytic ramp (`getRampY`) and therefore stays climbable. The whole rule is a single `LAND_ONLY` flag so it can be flipped off to restore the old "highest surface wins" behaviour. Confidence: 0.6
- When replacing a procedural 3D model builder, preserve its exact public contract (function signature, returned object keys, named pivots/sockets/anchors, userData, pose hooks) and edit only that builder; do not touch consumers. Confidence: 0.85
- For procedural 3D enemies, prefers ambitious high-detail low-poly stylized geometry when performance headroom exists (15k–25k triangles), all procedural with no external assets, layered armor/detail, reuse shared geometry/material caches, and castShadow on meshes. Confidence: 0.65
- Prefers new enemy/variant types to be wired natively (stats, rig, AI routing, death timing) through their own type key rather than aliased to an existing type via brittle post-construction overrides. Confidence: 0.7
- Manhua stat/UI terminology: keep internal stat keys (`str`, `int`, `vit`, `agi`, `wil`) intact so combat math never breaks, and change only the display labels to the manhua terms — `STRENGTH`, `INTELLIGENCE`, `STAMINA` (for `vit`), `DEXTERITY` (for `agi`), `WILLPOWER` (for `wil`) — plus manhua-style UI strings such as `UNIQUE SKILLS:` and `NAME (★)` / `NAME (★★)` headers. Never rename internal keys to match display labels. Confidence: 0.7
- HUD layout convention: panels that sit side by side in the HUD (e.g. the currency readout and the day badge) belong in one shared absolutely-positioned flex row (`topLeftBar`) — never place one of them with a hardcoded pixel offset (e.g. `left: 310px`), because the neighbouring readout grows with its text (bigger gold/ticket counts) and the fixed-offset element then slides on top of it and hides the value. Confidence: 0.7
