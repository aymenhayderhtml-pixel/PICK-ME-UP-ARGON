# Workflow taste
- Works in explicit stages: asks for code research and a written spec first, and states "Do NOT implement anything yet" until the plan is approved. Confidence: 0.85
- Delegates planning to an external AI planner (including a browser-based 3D-capable AI) that cannot see the repo: the agent authors one self-contained prompt embedding real code facts (file paths, function names + signatures, data structure fields/types, short code excerpts), then the planner's reply is pasted back for implementation. Confidence: 0.95
- Requires the planner prompt to be split into explicitly ordered, labeled parts (role/rules, code facts, game context, design spec, required output) with per-part content rules. Confidence: 0.75
- Requires research to report "NOT FOUND" for facts that do not exist instead of inventing them, and to quote real code rather than paraphrase. Confidence: 0.75
- Prefers read-only research subagents for code exploration: quote real code with paths/line numbers, never modify files. Confidence: 0.55
- Requires implementation plans to be phased, each phase small enough to finish and test alone, and each phase to specify files to create/edit, function names + signatures, data structures, config values, edge cases, and npm test scripts with expected results. Confidence: 0.8
- Wants every tunable number (emotion ranges, thresholds, multipliers, caps) in a central config file, presented as tables, never hardcoded in logic. Confidence: 0.8
- Requires a single shared code path for live gameplay and offline/catch-up simulation, with a seeded RNG so runs are deterministic and reproducible in tests. Confidence: 0.8
- States design constraints as explicit formulas and thresholds up front (ratios, floors, caps) and expects them proven by a numeric test (e.g. simulate N days, report the numbers). Confidence: 0.7
- Requires backward compatibility: new save fields need defaults plus a migration path for old saves, and existing systems (combat, weapon code) must not be broken. Confidence: 0.75
- Enumerates out-of-scope features explicitly and expects them marked "future" and excluded from the plan instead of silently dropped. Confidence: 0.7
- Expects a regression test to be added to the existing headless test script (e.g. `scripts/test_integration.mjs`) for each fixed live-game integration gap — exercising the real legacy entity mix and asserting the shared system's full API surface exists. Confidence: 0.6
- Expects a crash report to state whether the bug came from the current work or from pre-existing/untracked work, and to name the file/line evidence used to decide. Confidence: 0.6
- When a prompt is written to a file for copy-paste, expects the whole prompt wrapped in one fenced block (4-backtick outer fence when it contains nested code excerpts) so nested fences survive, and a fence-balance check run after writing. Confidence: 0.6
- Hands the external planner's reply back as a file in the repo (e.g. `docs/ARGON.md`) and expects the agent to locate and read that file rather than receive the plan pasted into chat. Confidence: 0.55
- Requires deterministic tests: any code path that rolls randomness must take an injected RNG or have `Math.random` pinned inside the test, so a suite never flakes between runs. Confidence: 0.55
- Expects the whole test suite to be run repeatedly (e.g. 3 consecutive passes) before declaring the work done, to prove the results are stable and not flaky. Confidence: 0.5
- Opens bug-fix requests with "read the agent md and fix this issue": the project's AGENTS.md is the authoritative rulebook (protected paths, forbidden browser verification, codemap obligation) and must be read before any code is touched. Also issues it as a standalone opener with no accompanying task ("read teh agent md", "read the agent md"), expecting AGENTS.md plus docs/CODEMAP.md to be loaded and the operating rules restated compactly before work starts — and then the session waits for the task rather than inventing one. Reinforced by another fresh standalone opener ("read the agent md") answered with a concern-grouped bullet summary of the rulebook (stack, workflow, testing, protected paths, code rules, codemap obligation, report format) closing with "Ready for your task." Confidence: 0.9
- At session start (e.g. a rulebook-only opener) expects the working tree to be audited proactively and reported: which files are modified/untracked, which of them sit in protected paths (e.g. `src/ui/RewardWindow.js`), and which are scratch dirs (e.g. `.tmp_manhua/`) — with a stated commitment to avoid clobbering them unless asked. Confidence: 0.55
- Expects navigation by the project's file index rather than broad scanning: use `docs/CODEMAP.md` (and its lookup table) to pinpoint the relevant files, open only what's needed, and avoid full-project scans. Confidence: 0.65
- After fixing a bug, expects the non-obvious invariant/trap behind it to be written into the codemap's Known Gotchas (e.g. "the roster window is viewport-capped; new hero-sheet sections must be appended to `detailBody`, never to `rightPanel`"; "never call `Math.pow(t, fractional)` with a `t` that can dip slightly negative — clamp to [0,1] first, or NaN lands in the position attribute and the mesh is frustum-culled away"; "the `enemy.isBoss` branch must pass `allies`, or a LEADER's rally aura throws `allies is not iterable`"), even when the change adds no files or exports. The entry is kept to ONE line, and only when the gotcha is genuinely worth keeping. Reinforced by a pure-layout bug (no module change at all): the HUD's hardcoded badge offset overlapping the currency readout still got its own one-line gotcha entry. Confidence: 0.7
- Works in this repo concurrently with other agents (other branches of the ARGON work touch different files at the same time): keep edits scoped to the files you own, and before declaring done verify with `git diff --stat` that your files were not clobbered or reverted by the other agent. Reinforced mid-push: file mtimes and `find -newermt` showed another agent editing the same tree seconds earlier, so the tree was re-verified (node --check on the in-flight files, codemap check, tests) before committing, and the other agent's WIP that got swept into the commit was named in the final report so their agent can reconcile against the moved HEAD. Confidence: 0.75
- Expects the codemap to stay in sync for a same-path redesign too: the existing file-index description gets rewritten to the new feature set and a new lookup-table row is added (e.g. "game settings (options window) → `OptionsWindow`") so future agents can find the surface, then `node scripts/check_codemap.mjs` is re-run. Confidence: 0.6
- To debug a browser-only runtime error under the no-browser rule, expects the real scene to be reproduced headlessly in Node: a throwaway scanner in the scratchpad that stubs the renderer and input, installs a minimal DOM/canvas shim, constructs the actual scene, ticks it, and walks the live scene graph to name the offending object (parent chain, geometry uuid, vertex index) instead of guessing from the stack trace. Confidence: 0.65
- Expects a newly-reported bug's search space to be narrowed with `git diff --stat` / `git status` on the working tree first (recently changed files are the likely culprits), then targeted greps for the writer of the bad value, rather than a full-repo read. Confidence: 0.6
- Expects shared harness code to be factored once and reused across diagnostic scripts (e.g. one `shim.mjs` exporting the DOM/canvas stubs) instead of copy-pasted into every scanner. Confidence: 0.5
- Expects throwaway diagnostic scripts to live in the session scratchpad and never be committed into the project, with the report stating that no project files were added. Confidence: 0.6
- Expects newly added browser-facing logic to be proven by a small headless Node test that stubs the browser API (e.g. a fake `window`/AudioContext) and asserts the specific invariants — no context created before a user gesture, exactly one shared context afterwards — instead of relying on manual browser verification. Confidence: 0.6
- When a headless harness surfaces a failure unrelated to the reported bug, expects live-game reachability to be proven from the spawn/branch conditions (e.g. the LEADER path is really taken because `hasLeader: floorNumber >= 2`) before calling it a real bug; reachable ones get a minimal one-line fix and are labelled pre-existing. Confidence: 0.6
- When the root cause lives in a protected file (e.g. `src/combat/Enemy.js`), expects the fix to be made at the call site instead, with the report stating the protected file was left untouched. Confidence: 0.6
- When fixing bugs flagged in a prior analysis, re-read each file before editing and treat any line numbers supplied as a guide only, because the code may have changed since the analysis was written. Confidence: 0.55
- Requires at least two test cases per fixed bug in the regression suite, and insists they cover edge cases (e.g. odd-count leftovers, protected/immortal entities, no-op/duplicate-emission paths, missing-resource toleration), not just the happy path. Confidence: 0.7
- Refactor tasks maintain a `REFACTOR_LOG.md` with three parts: an outline naming every method/function with its line range and group plus all exports and the singleton name; a statement of whether the source was a class (mixin pattern) or plain modules (thin forwarding); and a final `STEP N RESULT` section listing new files with line counts, the before/after comparison result, and problems. Confidence: 0.8
- For a class-based module split, use the mixin pattern (`export const XMixin = (Base) => class extends Base { ... }`) composed in the original class, which keeps the constructor, class fields, getters, setters, and static members; for a non-class module, use plain modules with thin forwarding so the public API is unchanged. Confidence: 0.75
- Move-only splits assign each top-level helper or constant to the single group that uses it; only helpers shared across groups stay in the original module and are exported. Confidence: 0.7
- Module-level state (caches, shared materials, counters, module-level variables) must be kept in a single module during a split and never duplicated across the new files; the group that owns it imports/uses it rather than re-declaring it. Confidence: 0.65
- No circular imports in a split: new modules must not import from the original module unless that import already existed before. Confidence: 0.7
- Before and after a stateful module split, capture a serialized-state snapshot (default state plus any sample save) and require the before/after output to be byte-identical, in addition to `node --check`, codemap, tests, and build. Confidence: 0.75
- Refactors of save/state modules must keep the save key and serialized data shape unchanged so old saves still load. Confidence: 0.75
- Refactor step commits use the exact requested commit message (e.g. ‘refactor step 6: GameState split’); for a multi-file refactor each file gets its own commit with the matching per-file message (e.g. ‘refactor step 10: prairie floor split’). Confidence: 0.7
- Treats a direct bug report as implicit approval to edit the protected file the bug lives in (e.g. a `src/ui/*` window named by the symptom) — no separate sign-off question — but keeps the change scoped to the reported surface, leaves sibling windows that share the flaw untouched, and lists them in the report's risks as out of scope. Confidence: 0.55
- Prompt-authoring task: when the ask is "write a ready-to-paste prompt for another coding session (Argon)", the agent must not write or change any game code — the only writes are docs (the prompt file, plus a follow-up task list). The prompt must be self-contained enough that a weak executor follows it with no guessing: exact file names, exact strings, exact numbers, and the exact target to extend (e.g. which builder function in `src/art/enemies.js` to extend and which stats line to add in `src/data/enemies.js`) instead of leaving it to pick its own path. Confidence: 0.75
- Reference-vs-implementation comparison: build a row-per-feature table of the source spec against the current game and mark every row MATCH / DIFFERENT / MISSING. Rows the spec does not state are never invented; anything the spec marks UNSURE is collected into an "Open questions" list rather than guessed at or silently dropped. Confidence: 0.7
- Deferred-work backlog: features the spec pushes out of the current task are written to a backlog doc (e.g. `docs/NEXT_TASKS.md`) as separate small tasks, each tagged with a size (small / medium / large) and the files likely involved, plus a "Conflicts with the game" section recording spec-vs-reality contradictions — which are documented, not fixed. Confidence: 0.7
- Reference source material: the manhua spec the tasks cite as `docs/MANHUA_NOTES.md` is not in the repo — the real source is chapter panel images (`.webp`) in the external lore folder. The agent locates them (glob/find/grep outside the repo), converts them to PNG with PIL and OCRs the panels with tesseract instead of stalling on the missing notes file. Image files must be copied inside the workspace directory before they can be read — copies in the session scratchpad do not render. Confidence: 0.65
- Cleanup/audit request flow: expect a written plan artifact presented for review, then a task ledger with one entry per phase, then execution only after approval. The plan should name exactly which files, exports, docs and artifacts get deleted or changed, cite file:line evidence for each claim, and carry an explicit "not doing" list. Confidence: 0.6
- Repo-hygiene stance: prefer aggressive removal of unreferenced material (zero-reference docs, stale build output, orphaned binaries/screenshot dirs) over keeping it; still-referenced one-time audit/QA reports get moved into an archive folder with an index README instead of being deleted or left mixed in with live docs. Confidence: 0.6
- Cleanup means cleanup, not refactor: remove dead files and dead exports, but leave live modules alone — no opportunistic dedupe/merge of duplicated helpers (e.g. two `createRng` implementations) unless explicitly asked. Also prefers repairing intended-but-broken dev tooling (dead debug cheats) rather than deleting it. Confidence: 0.6
- For destructive cleanup work, capture a baseline first (`git status`, `git log`, and a green test run) so later failures can be attributed, and route deletions through git (`git rm --cached` / `git mv` to `docs/archive/`) so every removal stays recoverable from history — then leave the commit itself to the user. Confidence: 0.6
- Push request: a terse "puch it to main" is approval to commit and push straight to `origin/main` — no feature branch, no PR, no side branch — and the push is confirmed afterwards by re-fetching and showing local main == origin/main (0 behind / 0 ahead) plus the commit SHA and diffstat. Confidence: 0.65
- Pre-push gate: before committing, fetch and compare ahead/behind with the remote (`git rev-list --left-right --count origin/main...main`), then re-run the codemap checker, the npm test suite and the production build, so only a verified tree lands on main. Confidence: 0.6
- Staging scope on commit: stage the whole tree (`git add -A`) except tool-managed and scratch directories — the agent's own `.commandcode/` preference files and `.tmp_*` art-source scratch dirs — so the commit carries only project code and docs, and the exclusions are listed in the final report. Confidence: 0.55
- At task start, expects `AGENTS.md` and `docs/CODEMAP.md` to be read first (rulebook + file index) before any code is touched. Confidence: 0.7
- For parallel-agent work, treats a stated file lock as absolute: only the explicitly listed files may be edited, and new functionality should be added by extending existing exported objects/functions rather than adding or renaming top-level exports so `docs/CODEMAP.md` stays untouched. Confidence: 0.8
- In parallel-agent tasks, user grants a strict file allowlist ("STRICT FILE LOCK"): edit only the explicitly named files and touch no others; leave out-of-scope surfaces untouched and list them as skipped in the final report. Refactor tasks are scoped the same way: only the named files, the new files, `docs/CODEMAP.md`, and `REFACTOR_LOG.md` may be edited. Confidence: 0.75
- Uses a two-stage external AI pipeline for 3D replacement work: a browser 3D AI (Argon) generates the replacement from a report plus a reference image, then the implementation AI (Gemini) integrates it with an exact instruction to replace only the named builder, keep everything else working, run the game, and fix errors. Confidence: 0.65
